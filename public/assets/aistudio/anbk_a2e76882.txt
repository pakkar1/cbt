# MASTER PROMPT — PLATFORM UJIAN SMP BERBASIS WEB

## 1. PERAN DAN TUJUAN

Bertindaklah sebagai Senior Full-Stack Engineer, Software Architect, Database Engineer, UI/UX Designer, Cybersecurity Engineer, dan Performance Engineer yang berpengalaman membangun platform asesmen pendidikan berskala besar.

Bangun aplikasi ujian sekolah berbasis web yang memiliki alur, pola navigasi, tata letak ruang ujian digital, mekanisme pengerjaan, pengelolaan waktu, penandaan soal, navigasi nomor soal, dan proses penyelesaian yang menyerupai pengalaman Asesmen Nasional Berbasis Komputer (ANBK) dan Tes Kemampuan Akademik (TKA) tingkat SMP.

Aplikasi harus mempunyai identitas, nama, logo, dan desain orisinal sendiri. Jangan menggunakan logo pemerintah, mengeklaim sebagai aplikasi resmi pemerintah, atau menyalin aset berhak cipta yang tidak disediakan secara sah.

Nama aplikasi sementara: **SMP Digital Assessment Platform**. Buat nama aplikasi, logo, warna utama, dan identitas sekolah dapat diubah melalui panel administrator.

Tujuan utama:
1. Menyelenggarakan ujian online untuk siswa kelas 7, 8, dan 9 SMP.
2. Menampung total sekitar 1.000 siswa.
3. Menyelenggarakan ujian dalam 6 sesi per hari selama 13 hari.
4. Mendukung kapasitas konfigurasi maksimal 120 peserta per sesi.
5. Mendukung banyak mata pelajaran, bank soal, jadwal ujian, proktor, token ujian, dan analisis hasil.
6. Memprioritaskan keamanan, keakuratan data, kestabilan, kemudahan penggunaan, serta biaya operasional serendah mungkin.
7. Menghasilkan aplikasi nyata yang berfungsi, bukan hanya desain, demo, atau mockup.

Jangan hanya menampilkan data contoh. Seluruh fungsi produksi harus terhubung ke backend dan database. Data demo hanya boleh digunakan pada lingkungan pengembangan dan harus dipisahkan dari data produksi.

## 2. TEKNOLOGI WAJIB

Gunakan stack berikut:

- Frontend: React + TypeScript.
- Build tool: Vite atau konfigurasi React yang kompatibel dengan Vercel.
- Styling: Tailwind CSS atau sistem CSS modular yang konsisten.
- Komponen UI: reusable, responsif, aksesibel, dan ringan.
- Routing: React Router atau router kompatibel.
- Backend: Vercel Serverless Functions menggunakan TypeScript.
- Database: Firebase Cloud Firestore.
- Authentication: Firebase Authentication.
- Backend database access: Firebase Admin SDK, hanya di server.
- Validasi data: Zod atau library validasi setara.
- Pengujian: Vitest dan React Testing Library; gunakan pengujian API sesuai kebutuhan.
- Version control: Git dan GitHub.
- Hosting: Vercel untuk frontend dan endpoint API.
- Database dan autentikasi: Firebase.

Gunakan package stabil yang saling kompatibel. Jangan menggunakan library yang tidak diperlukan.

Jangan menggunakan PHP, MySQL, PDO, atau backend yang tidak sesuai dengan arsitektur di atas.

Jangan pernah menaruh Firebase Admin SDK credentials, private key, token rahasia, atau kunci jawaban ujian di frontend.

Gunakan environment variables:
- VITE_FIREBASE_API_KEY
- VITE_FIREBASE_AUTH_DOMAIN
- VITE_FIREBASE_PROJECT_ID
- VITE_FIREBASE_APP_ID
- FIREBASE_PROJECT_ID
- FIREBASE_CLIENT_EMAIL
- FIREBASE_PRIVATE_KEY

Sesuaikan konfigurasi dengan kebutuhan nyata. Semua variabel VITE_ hanya untuk konfigurasi frontend yang memang aman dipublikasikan. Variabel server harus disimpan dalam Vercel Environment Variables dan tidak boleh dikirim kepada browser.

Jika memungkinkan, gunakan kredensial service account melalui mekanisme aman yang didukung deployment. Jangan pernah memasukkan kredensial ke GitHub atau file frontend.

Sediakan `.env.example` tanpa nilai rahasia yang sebenarnya.

- Melihat ujian yang ditugaskan.

- Memasuki ujian dengan autentikasi yang valid.

- Mengerjakan soal.

- Menyelesaikan dan mengirimkan ujian.

## 11. TOKEN MULAI DAN TOKEN SUBMIT

Implementasikan dua jenis token yang berbeda.

### Token mulai ujian
- Dibuat atau diterbitkan oleh proktor yang berwenang.
- Terikat pada sesi ujian tertentu.
- Berlaku hanya dalam rentang waktu yang ditetapkan.
- Tidak boleh digunakan untuk sesi lain.
- Memiliki batas percobaan.
- Memiliki masa berlaku.
- Disimpan dalam bentuk hash apabila memungkinkan.
- Tidak ditampilkan kepada peserta yang tidak berhak.
- Dapat dicabut dan diterbitkan ulang sesuai izin.

### Token submit
Sediakan opsi untuk mewajibkan token penyelesaian.

Jika kebijakan sekolah mengaktifkannya:
- Token submit baru dapat diterbitkan setelah 45 menit sejak waktu mulai resmi peserta atau waktu mulai sesi, sesuai konfigurasi administrator.
- Waktu acuan harus berasal dari backend.
- Peserta tidak boleh memanipulasi jam komputer untuk mempercepat penerbitan token.
- Token hanya berlaku untuk attempt dan sesi terkait.
- Token memiliki masa berlaku dan batas percobaan.
- Penerbitan, penggunaan, dan kegagalan validasi dicatat dalam audit log.

Sediakan pengaturan apakah submit boleh dilakukan tanpa token setelah durasi minimum tercapai, agar kebijakan dapat disesuaikan.

Penting: token submit tidak boleh menghalangi pengiriman otomatis ketika deadline resmi telah berakhir. Sistem harus mempunyai mekanisme penyelesaian darurat yang aman jika proktor tidak tersedia atau terjadi gangguan teknis.

Jangan menggunakan token sebagai satu-satunya mekanisme autentikasi. Setiap permintaan tetap harus memvalidasi identitas, hak akses, attempt, sesi, dan status ujian.

## 12. PENYIMPANAN JAWABAN DAN PEMULIHAN KONEKSI

Ini merupakan fitur kritis.

Implementasikan:
- Autosave ketika jawaban berubah.
- Debounce untuk menghindari permintaan berlebihan.
- Penyimpanan berkala sebagai perlindungan tambahan.
- Indikator status penyimpanan.
- Retry dengan exponential backoff dan jitter.
- Idempotency key untuk operasi yang berisiko duplikasi.
- Sinkronisasi ketika koneksi kembali.
- Pemulihan attempt setelah browser dimuat ulang.
- Penanganan konflik perubahan.
- Validasi batas waktu pada server.
- Pengiriman jawaban final secara idempoten.

Gunakan IndexedDB untuk antrean lokal jawaban yang belum berhasil disinkronkan, jika sesuai. Simpan hanya data minimum yang dibutuhkan. Lindungi data lokal dari kebocoran pada perangkat bersama dan hapus cache sensitif setelah ujian berakhir sesuai kebijakan.

Jangan pernah menandai jawaban sebagai tersimpan di server sebelum server mengonfirmasi keberhasilan penyimpanan.

Jika koneksi putus:
1. Tampilkan peringatan yang jelas.
2. Pertahankan jawaban lokal sementara.
3. Jangan membuat attempt baru.
4. Lakukan sinkronisasi kembali ketika koneksi pulih.
5. Jangan menerima jawaban setelah deadline hanya karena jawaban tersimpan secara lokal.
6. Tampilkan status sinkronisasi yang sebenarnya.

Sistem harus membedakan:
- Jawaban tersimpan di server.
- Jawaban tersimpan lokal tetapi belum tersinkronisasi.
- Jawaban gagal disimpan.

## 13. TIMER DAN FINALISASI

Gunakan waktu server sebagai acuan.

Timer di browser hanya untuk visualisasi. Backend wajib memeriksa deadline pada setiap operasi yang relevan.

Saat waktu habis:
- Attempt harus ditutup secara otomatis melalui mekanisme backend yang andal.
- Jawaban terakhir yang sudah berhasil tersimpan harus dipertahankan.
- Jawaban lokal yang belum tersinkronisasi tidak boleh dianggap tersimpan di server.
- Status attempt berubah menjadi AUTO_SUBMITTED atau status final yang sesuai.
- Nilai dihitung setelah validasi.
- Peristiwa dicatat dalam audit log.

Jangan hanya mengandalkan JavaScript setInterval pada browser untuk menutup ujian.

Implementasikan mekanisme penutupan otomatis yang realistis untuk deployment serverless. Jika tidak menggunakan scheduler, setiap permintaan yang relevan harus memeriksa deadline, dan sistem harus menyediakan proses rekonsiliasi untuk menemukan attempt kedaluwarsa.

Finalisasi harus idempoten. Klik submit berkali-kali tidak boleh membuat nilai ganda atau mengubah hasil final.

Struktur tersebut boleh disesuaikan selama relasi, keamanan, dan performanya lebih baik.

Setiap dokumen harus mempunyai ID, timestamp yang sesuai, serta field status yang tervalidasi.

Pisahkan data publik dari data privat.

Pisahkan kunci jawaban dari konten soal yang dikirim ke browser.

Simpan jawaban peserta dalam dokumen yang dibatasi per attempt atau kelompok soal agar ukuran dokumen tidak terus membesar. Perhatikan batas ukuran dokumen Firestore dan biaya baca/tulis.

Gunakan transaksi atau operasi atomik yang sesuai untuk:
- Klaim attempt aktif.
- Validasi token.
- Finalisasi ujian.
- Penetapan status.
- Pencegahan duplikasi submission.

Rancang indeks Firestore untuk query yang benar-benar digunakan. Sertakan konfigurasi indeks yang diperlukan.

Jangan menggunakan satu dokumen global yang terus diperbarui oleh seluruh peserta sebagai counter, karena berpotensi menjadi bottleneck.

## 17. KEAMANAN FIREBASE DAN API

Buat Firestore Security Rules dengan prinsip default deny.

Jangan mempercayai data role dari localStorage, parameter URL, atau objek request yang dibuat pengguna.

Backend harus memverifikasi Firebase ID token untuk setiap endpoint privat dan memeriksa otorisasi berdasarkan data yang terpercaya.

Gunakan Firebase Admin SDK hanya di server.

Jika server menggunakan Admin SDK, ingat bahwa akses tersebut tidak otomatis dibatasi oleh Firestore Security Rules. Karena itu, setiap endpoint backend harus menerapkan pemeriksaan otorisasi sendiri.

Terapkan:
- Validasi input di server.
- Pembatasan ukuran request.
- Rate limiting yang sesuai.
- Pencegahan brute force token.
- Sanitasi konten.
- Pembatasan CORS.
- Proteksi terhadap IDOR.
- Validasi kepemilikan attempt.
- Pencegahan pengiriman ulang yang tidak sah.
- Audit log untuk operasi sensitif.
- Pesan error yang tidak membocorkan informasi rahasia.

Jangan mengeklaim aplikasi anti-cheat sempurna. Browser biasa tidak dapat menjamin bahwa siswa tidak membuka tab lain, menggunakan perangkat kedua, atau mengambil foto layar.

Sediakan fitur pembatasan navigasi dan peringatan sesuai kemampuan browser, tanpa mengganggu aksesibilitas atau merusak browser siswa.

## 18. HASIL DAN ANALISIS NILAI

Dukung penilaian:
- Pilihan ganda satu jawaban.
- Pilihan ganda kompleks.
- Benar/salah.
- Menjodohkan.
- Isian singkat dengan aturan penilaian yang dapat dikonfigurasi.
- Uraian dengan rubrik penilaian manual.

Untuk pilihan ganda satu jawaban, nilai berdasarkan kunci dan bobot yang tersimpan di server.

Untuk pilihan ganda kompleks, sediakan beberapa metode penilaian yang dapat dipilih administrator, misalnya exact match atau partial credit. Jangan memberikan nilai parsial jika kebijakan tersebut tidak diaktifkan.

Untuk jawaban uraian, sediakan:
- Rubrik.
- Skor minimum dan maksimum.
- Catatan penilai.
- Status belum dinilai, sedang dinilai, dan sudah dinilai.
- Riwayat perubahan nilai.
- Identitas penilai.

Tampilkan:
- Nilai per siswa.
- Nilai per kelas.
- Nilai per mata pelajaran.
- Nilai per sesi.
- Rata-rata.
- Median.
- Nilai tertinggi dan terendah.
- Distribusi nilai.
- Persentase ketuntasan berdasarkan batas yang ditentukan.
- Jumlah benar dan salah jika sesuai jenis soal.
- Analisis butir soal.
- Tingkat kesulitan empiris berdasarkan hasil peserta.
- Daya pembeda jika ukuran dan karakteristik data mendukung analisis tersebut.

Bedakan nilai yang sudah final dari nilai yang masih menunggu penilaian uraian.

Sediakan ekspor CSV dan laporan PDF. Jangan membocorkan hasil siswa kepada role yang tidak berhak.

## 20. KINERJA DAN SKALA

- Lazy loading.
- Pagination.
- Query Firestore.
- Jumlah listener.
- Frekuensi autosave.
- Pengiriman jawaban.
- Ukuran payload.
- Penggunaan cache yang aman.
- Penanganan error dan retry.

Jangan mengambil data yang sama secara berulang tanpa kebutuhan.

Buat strategi pengujian beban untuk:

Gunakan load testing di lingkungan pengujian dengan data sintetis, bukan dengan menyerang sistem produksi.

Dokumentasikan keterbatasan paket gratis Vercel dan Firebase. Jangan mengasumsikan seluruh layanan memiliki kuota gratis tanpa batas.

Buat perkiraan jumlah operasi baca/tulis berdasarkan asumsi jumlah soal, durasi ujian, frekuensi autosave, dan jumlah peserta. Jelaskan bagian yang perlu diukur sebelum hari pelaksanaan.
